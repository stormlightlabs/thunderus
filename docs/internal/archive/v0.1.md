# v0.1 Internal Feature Archive

This archive keeps the durable decisions from completed v0.1 internal plans
after their feature-local `plan.md` and `tasks.md` files were removed.

## Configuration

Config resolves in a fixed order: CLI flags, `THNDRS_` environment variables,
project TOML, global TOML, then built-in defaults.

Supported config files are `~/.thndrs/config.toml` and `.thndrs/config.toml`.
Ordinary config keys cover runtime defaults and discovery roots: `model`,
`websearch`, `tick_rate_ms`, `theme`, `mouse`, `verbose`, `skill_dirs`,
`session_dir`, and `default_workspace`. `--cwd`, `--print-prompt`,
`--no-alt-screen`, and `--no-mouse` stay CLI-only.

Effective config metadata is recorded for diagnostics, prompt inspection,
sessions, and inspect/export output. Provider secrets stay outside TOML and
outside `THNDRS_` config; secret-shaped TOML keys are rejected, and tests prove
secrets are not serialized into UI or session surfaces.

## Tool Registry

Built-in tools use registry-backed entries instead of a central schema/dispatch
match. Each tool module owns its model-visible definition, parsing, execution,
output mapping, and structured side-effect metadata.

Existing tool names stayed stable; legacy aliases such as `read`, `write`,
`edit`, `bash`, and `research` were not added. File, web, URL, write, and shell
tools moved into module-owned boundaries, and all providers receive the same
derived catalog.

The migration preserved workspace containment, URL safety checks, output caps,
timeouts, truncation metadata, background process registration, file-write
audit records, and shell audit records.

## MCP

MCP adds external tool discovery and invocation through the official Rust SDK
while keeping local `thndrs` safety policy.

MCP config files are `~/.thndrs/mcp.toml` and `.thndrs/mcp.toml`. Project
server definitions override user definitions by server name. Supported
transports are `stdio` and `streamable_http`, and tools are exposed as
`mcp__{server}__{tool}`.

The CLI can list, test, inspect, and call MCP tools. Disabled, skipped, failed,
and ready servers produce bounded diagnostics instead of crashing startup.
`McpClient` and `McpManager` handle transports, cached tools, namespaced
routing, output conversion, timeouts, bounded stderr, redaction, and child
cleanup. MCP calls are recorded in session JSONL and inspect/export output.

## ACP Client

ACP support lets `thndrs` run external agents while preserving the local UI,
cancellation, permission, session, and tool safety model.

ACP agents are configured under `[acp_agents.<name>]` and selected with
`--model acp:<name>`. Assistant text, reasoning/status updates, usage, tool
calls, failures, and cancellation flow through the normal transcript and
session path. Permission requests pause the turn and show one focused decision
at a time.

The runtime lives under `src/acp/` and uses `agent-client-protocol = "1.0.1"`
behind the existing event stream. Built-in providers stay on the provider
harness; only `acp:<name>` routes through ACP. Local session ids remain
separate from opaque ACP ids, and session metadata omits raw protocol lines and
credentials.

Filesystem callbacks are workspace-contained and audited like built-in tools.
Terminal callbacks use argv-only execution, workspace cwd policy, capped
output, cancellation/kill/release cleanup, and shell audit. ACP auth state is
agent-owned.

CLI support includes `acp list`, `acp inspect`, `acp smoke`, `acp logout`,
agent-owned session commands, registry discovery, install/update metadata
writes for supported `npx` and `uvx` entries, and MCP-over-ACP config passing.

## Provider Expansion

Provider expansion added OpenCode Zen Big Pickle as the default provider,
ChatGPT-backed Codex as an experimental provider, and TTFT statusline
observability.

OpenCode Zen uses `opencode/<model-id>` with `opencode/big-pickle` as the
initial default model and `OPENCODE_ZEN_KEY` as its credential. OpenCode Go
remains `opencode-go/` with `OPENCODE_GO_KEY`.

ChatGPT Codex uses `chatgpt-codex/<model-id>` for subscription-backed models
and is labeled ChatGPT-backed/experimental rather than OpenAI Platform API-key
access. Known picker entries include `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, and
`gpt-5.3-codex-spark`.

ChatGPT Codex auth uses device-code login first and browser PKCE fallback.
Refreshable credentials live under `~/.thndrs/auth.json` with Unix `0600`
permissions where supported. `CHATGPT_CODEX_ACCESS_TOKEN` can override stored
credentials for one process. ChatGPT Codex never falls back to `OPENAI_API_KEY`.

Both providers normalize streaming into the existing `ProviderTurn` and event
path. TTFT is measured from local submit to first semantic model output and
remains one user-observed value across retries.

Ignored live tests cover real credential, network, subscription, limited-free,
privacy, streaming, tool-call, login, and refresh prerequisites.

## Setup UX And ChatGPT OAuth

The setup flow is provider-aware instead of API-key-only. Public provider
argument values stayed stable: `umans`, `opencode-go`, `opencode-zen`, and
`chatgpt-codex`.

`thndrs setup` starts with workspace, model, provider, and auth status. In
interactive mode it shows a provider picker with OpenCode Zen Big Pickle as
the default. API-key providers keep hidden key entry, credential-store
selection, validation, idempotent model config writes, and project
git-exclude behavior.

OpenCode Zen setup copy calls out `OPENCODE_ZEN_KEY`, the limited-free offer,
and the free-period data-use caveat. ChatGPT Codex setup and login share OAuth:
setup does not ask for ChatGPT API keys, does not store ChatGPT credentials in
`.thndrs/credentials.env`, and can still write the selected default model when
confirmed.

The TUI recovery surface is provider-aware. API-key providers offer key entry,
switching, instructions, continue, and quit actions. ChatGPT Codex shows a
missing OAuth credential and starts an in-TUI device-code flow that renders the
verification URL and user code, polls on ticks, supports Esc cancellation, and
preserves the prompt draft.

Slash commands follow the same split: `/setup` opens provider-aware recovery,
`/login chatgpt-codex` opens ChatGPT OAuth recovery, `/login` for API-key
providers opens hidden key entry, and `/logout chatgpt-codex` stays CLI-only.
Slash-command arguments that look like secrets are rejected.

## Terminal UI

The v0.1 TUI moved to a transcript-first, row-owned renderer with a compact
bottom prompt, native scrollback for committed history, and bounded focused
surfaces for transient interaction.

The renderer projects app state into semantic view records before building
rows. The terminal backend still owns viewport diffs, cursor movement, resize
handling, and scrollback commits.

The prompt supports multi-line input, Unicode cursor placement, command mode,
suggestions, `@` file mentions, `Ctrl+P` file picking, queued input while
running, retryable failures, and visible stop/cancel state. Submitted
follow-ups are summary-only.

Transcript rows are typed and snapshot-covered. Long or failed tool output
stays compact in the transcript and opens through detail surfaces. `Ctrl+O`
opens the latest expandable detail, preferring failed/truncated tool output,
edit diffs, then warning/error detail.

The orientation/status area shows workspace, model/provider, run state,
session, TTFT when available, and the explicit trust wording
`local user · workspace-contained tools · no TUI sandbox`. That is UI wording,
not a new security boundary.

iocraft was adopted narrowly for bounded surfaces behind
`src/cli/renderer/adapter.rs`. It renders declarative elements to an
inspectable canvas and converts them back to `Row`/`Span`; it does not call
fullscreen or render-loop APIs from the TUI and does not own app state. The
live UI currently routes command picker, file picker, and help through this
path.

Permission prompts, first-run recovery, the prompt editor, committed transcript
rows, and tool details remain direct-rendered where that path preserves richer
behavior or stricter priority. Structured tables use explicit widths,
alignment, selected-row treatment, and narrow fallbacks.

The iocraft follow-up is tracked in
`docs/internal/features/012_iocraft/plan.md`: expand bounded surfaces through
the adapter while keeping the main prompt editor and committed transcript on
the direct row path.
