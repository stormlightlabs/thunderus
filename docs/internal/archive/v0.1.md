# v0.1 Internal Feature Archive

This archive keeps the useful decisions from completed v0.1 internal plans
after their feature-local `plan.md` and `tasks.md` files were removed.

## Configuration

`thndrs` now has a strict, explainable configuration contract. Effective
configuration resolves in this order: CLI flags, `THNDRS_` environment
variables, project TOML, global TOML, then built-in defaults.

Supported config files are `~/.thndrs/config.toml` and `.thndrs/config.toml`.
Unsupported pre-release spellings are ignored. Ordinary config keys cover
runtime defaults and discovery roots: `model`, `websearch`, `tick_rate_ms`,
`theme`, `mouse`, `verbose`, `skill_dirs`, `session_dir`, and
`default_workspace`. `--cwd`, `--print-prompt`, `--no-alt-screen`, and
`--no-mouse` stay CLI-only.

Effective config metadata is recorded for startup diagnostics, prompt
inspection, sessions, and inspect/export output. That metadata includes loaded
files, key origins, diagnostics, provider/model, search mode, workspace,
session directory, loaded `AGENTS.md` metadata, and activated skill metadata.

Provider secrets stay outside TOML and outside `THNDRS_` config. Secret-shaped
TOML keys are rejected, provider secret env vars are documented separately, and
tests prove secrets are not serialized into diagnostics, logs, prompt
inspection, session metadata, snapshots, or export metadata.

Deferred: LSP configuration, repository search internals, provider-private
state, permission rules, plugins, commands, workflows, session search, skill
marketplace/install/publishing, and subagent orchestration all remain separate
features.

## Tool Registry

The built-in tool layer now uses registry-backed tool entries instead of a
central schema/dispatch match. Each tool module owns its model-visible
definition, argument parsing, execution, output mapping, and structured
side-effect metadata.

Existing `thndrs` tool names stayed stable. Legacy names such as `read`,
`write`, `edit`, `bash`, and `research` were not added as aliases.

Read-only file tools, web search, URL reading, write tools, and shell execution
were moved into module-owned boundaries. Provider prompt assembly now receives
the derived registry catalog, and fake, Umans, Anthropic, OpenAI-compatible,
and OpenCode provider paths see identical tool definitions.

The migration preserved workspace containment, URL safety checks, output caps,
timeouts, truncation metadata, background process registration, file-write
audit records, and shell audit records.

Deferred: MCP tools enter through the external-tool path, memory tools wait for
the context/memory contract, and the registry is not a general plugin
framework.

## MCP

MCP support adds external tool discovery and invocation through the official
Rust MCP SDK while keeping local `thndrs` safety policy.

MCP config files are `~/.thndrs/mcp.toml` and `.thndrs/mcp.toml`. Project
server definitions override user definitions by server name. Supported
transports are `stdio` and `streamable_http`; tool names are exposed as
`mcp__{server}__{tool}`.

The CLI can list servers, test a server, list server tools, and call a tool:
`thndrs mcp list`, `thndrs mcp test <name>`,
`thndrs mcp tools <name>`, and
`thndrs mcp call <server> <tool> --json <args>`. The TUI can list configured
servers and tools. Disabled, skipped, failed, and ready servers produce
bounded diagnostics instead of crashing ordinary startup.

Implementation uses `rmcp` behind a small adapter for initialize, tool
listing, stdio process transport, Streamable HTTP transport, and tool calls.
`McpClient` and `McpManager` handle configured servers, cached tool lists,
namespaced routing, shared output conversion, timeout behavior, bounded stderr,
redaction, and child cleanup.

MCP calls are recorded in session JSONL with original server/tool metadata and
are included in inspect/export. Manual smoke tests covered the public memory
and filesystem MCP servers through `mcp test`, `mcp tools`, and `mcp call`.

Deferred: MCP cannot rewrite built-in schemas, prompt identity, or local safety
rules. Marketplace, installer, GUI surfaces, and a separate MCP-specific
permission system are out of scope.

## ACP Client

ACP client support lets `thndrs` run external ACP agents while preserving the
local UI, cancellation, permission, session, and tool safety model.

ACP agents are configured under `[acp_agents.<name>]` and selected with
`--model acp:<name>`. Assistant text, reasoning/status updates, usage, tool
calls, failures, and cancellation flow through the normal transcript and
session path. Permission requests pause the turn and show one focused decision
at a time.

The ACP runtime lives under `src/acp/` and uses
`agent-client-protocol = "1.0.1"` behind the existing event stream. Built-in
provider models stay on the existing provider harness; only `acp:<name>` routes
through ACP. Local `thndrs` session ids remain separate from opaque ACP session
ids, and session metadata omits raw stdio protocol lines and credential
material.

Filesystem callbacks are workspace-contained and audited like built-in tools.
Terminal callbacks use argv-only execution, workspace cwd policy, capped
output, cancellation/kill/release cleanup, and shell audit. ACP auth state is
agent-owned; any future client-owned credential flow needs a separate OS
credential-store design.

CLI support includes `acp list`, `acp inspect`, `acp smoke`, `acp logout`,
agent-owned session commands, registry discovery, install/update metadata
writes for supported `npx` and `uvx` entries, and MCP-over-ACP config passing.

Deferred: stdio remains the ACP client transport. Remote/custom ACP transport
planning moved to `docs/internal/features/009_acp_agent_server/`, and the
`thndrs`-provided MCP self-proxy remains a separate trust-boundary design.

## Provider Expansion

Provider expansion added OpenCode Zen Big Pickle as the default provider path,
ChatGPT-backed Codex as an explicit experimental provider, and TTFT statusline
observability.

OpenCode Zen uses the `opencode/<model-id>` prefix. The initial supported model
is `opencode/big-pickle`, which sends raw model id `big-pickle` to
`https://opencode.ai/zen/v1/chat/completions`. Zen model discovery uses
`https://opencode.ai/zen/v1/models` for validation and picker refresh, but the
client does not infer pricing or privacy behavior from discovery metadata.

OpenCode Go remains separate. `opencode-go/` keeps the existing Go semantics and
`OPENCODE_GO_KEY`; OpenCode Zen uses `opencode/` and `OPENCODE_ZEN_KEY`.
Missing Zen credentials recover through setup/login without silently changing
away from the default model. Public docs and setup copy keep OpenCode's Big
Pickle caveats visible: free access is time-limited, and collected data may be
used to improve the model during the free period.

ChatGPT Codex uses the `chatgpt-codex/<model-id>` prefix for
subscription-backed Codex models. The known picker entries are
`chatgpt-codex/gpt-5.5`, `chatgpt-codex/gpt-5.4`,
`chatgpt-codex/gpt-5.4-mini`, and
`chatgpt-codex/gpt-5.3-codex-spark`. This provider targets
`https://chatgpt.com/backend-api/codex/responses`, so it is labeled
ChatGPT-backed and experimental rather than a stable OpenAI Platform API route.

ChatGPT Codex auth uses device-code login first and browser PKCE with
`http://localhost:1455/auth/callback` as the fallback. Stored credentials live
under `~/.thndrs/auth.json` with Unix `0600` permissions where supported. The
stored entry contains access token, refresh token, expiry, and account id.
`CHATGPT_CODEX_ACCESS_TOKEN` can override stored credentials for one process
without writing credential storage. ChatGPT Codex never falls back to
`OPENAI_API_KEY`; account id is derived from the expected ChatGPT auth JWT claim
and fails closed when missing.

Both providers normalize streaming output into the existing `ProviderTurn` and
agent-event path. The stream parsers cover assistant text, visible reasoning
when present, function/tool-call deltas, completed tool calls, usage,
completion states, backend errors, and malformed protocol failures. Retry policy
keeps transient throttling, server errors, timeouts, and connection resets
retryable while treating missing credentials, invalid model ids, auth failures,
subscription/quota/balance failures, unavailable models, ended free periods,
and malformed post-connection protocol events as terminal.

TTFT is measured as client-observed latency from local turn submission to the
first semantic model-output event: assistant text, visible reasoning, tool-call
delta, or completed tool call. Provider status messages and usage-only events
do not stop the timer. Retries preserve one user-observed TTFT for the whole
turn. The TUI statusline can show `ttft: pending`, millisecond values below one
second, second values above that, and the last completed turn's TTFT while
space allows.

Ignored live tests cover Zen model listing, Big Pickle text streaming and tool
calls, ChatGPT Codex login flows, ChatGPT Codex streaming and tool calls, and
expired-token refresh. They stay skipped by default and name their real
credential, network, subscription, limited-free, and privacy prerequisites.

Deferred: additional OpenCode Zen endpoint families such as Anthropic Messages,
Responses, and Google model routes need fixture-backed stream/tool-call
captures before support. ChatGPT backend protocol drift needs periodic review
because the endpoint is not documented as a stable third-party Platform API.
Server-side TTFT should remain separate unless a provider exposes trustworthy
timing metadata.

## Setup UX And ChatGPT OAuth

The first-run setup flow was reshaped around provider auth kinds instead of an
API-key-only model. Public provider argument values stayed stable:
`umans`, `opencode-go`, `opencode-zen`, and `chatgpt-codex`.

`thndrs setup` now starts with a concise summary of workspace, selected model,
provider, and auth status. When interactive and no provider is forced, it shows
an explicit provider picker with OpenCode Zen Big Pickle as the default,
followed by ChatGPT Codex, Umans, and OpenCode Go. API-key providers keep
hidden key entry, global/project credential-store selection, validation,
idempotent model config writes, and project git-exclude behavior.

OpenCode Zen setup copy calls out the required `OPENCODE_ZEN_KEY`, the
time-limited free Big Pickle offer, and the free-period data-use caveat before
credential entry. The default model remains `opencode/big-pickle`.

ChatGPT Codex setup and login share the same ChatGPT OAuth path. Normal setup
does not ask for a ChatGPT API key or access token, does not ask for
global/project credential storage for auth, and never stores ChatGPT
credentials in `.thndrs/credentials.env`. Refreshable credentials live in
`~/.thndrs/auth.json`, while `CHATGPT_CODEX_ACCESS_TOKEN` remains a
process-local override for automation and debugging.

Non-interactive ChatGPT setup fails with OAuth-specific instructions unless
ChatGPT auth is already available. If the process has
`CHATGPT_CODEX_ACCESS_TOKEN`, setup reports environment auth and may optionally
create or update stored OAuth credentials when run interactively. ChatGPT setup
can still write the selected default model to global or project config when the
user explicitly confirms it.

The TUI recovery surface became provider-aware. API-key providers show an API
key recovery path with actions to enter a key, switch model/provider, show
instructions, optionally continue, or quit. ChatGPT Codex shows a missing
ChatGPT OAuth credential and starts an in-TUI device-code flow instead of
hidden API-key entry. The focused surface renders the verification URL and user
code, polls on ticks without blocking prompt rendering, supports Esc
cancellation without writing credentials, stores successful credentials through
the shared auth writer, and preserves the prompt draft across success,
cancellation, and failure.

Slash commands follow the same split: `/setup` opens provider-aware recovery,
`/login chatgpt-codex` opens ChatGPT OAuth recovery, `/login` for API-key
providers opens hidden key entry, and `/logout chatgpt-codex` stays CLI-only.
Slash-command arguments that look like secrets are rejected.

Deferred: live OAuth, browser PKCE fallback, and real OpenCode key smoke tests
remain manual release QA because they require real accounts, credentials, and
network access.
