# v1 Spec

v1 defines the supported user-facing contract for `thndrs` after the alpha
surface settles. Completed alpha behavior lives in the book and internal notes;
this file tracks remaining v1 work.

## Release Goal

Goal: define the supported user-facing contract and make the harness predictable
enough to install and use repeatedly.

Required:

- Config file support with CLI/env overrides and clear precedence.
- Read-only LSP-backed code intelligence works where a language server exists.
- Session inspect/export can read sessions without opening the TUI.
- Skill engine support for reusable task instructions with progressive
  disclosure.
- Agent self-knowledge for current prompt assembly, loaded resources, active
  tools, and `thndrs` docs.
- Release notes follow a changelog format.
- Packaging supports at least `cargo install`.
- CI runs formatting, clippy, unit tests, snapshot tests, and no-network provider
  fixture tests.
- Upgrade behavior is documented for alpha session/config changes.

## Public Contract

For this CLI app, the remaining or still-unsettled v1 public contract includes:

- Config file path and keys.
- LSP tool names, inputs, outputs, and no-server fallback behavior.
- Skill discovery, activation, loading, validation, and precedence rules.
- Remote skill loading and reference traversal limits.
- Agent self-description/introspection output shape.
- Exit codes for non-TUI commands.
- Documented install and upgrade workflow.

## CLI And Config

v1 may add non-TUI `inspect` and `export` commands once sessions exist.

Config precedence:

1. CLI flags.
2. Environment variables.
3. Config file.
4. Built-in defaults.

Config should cover:

- Default model.
- Web search mode.
- Session path.
- Tick rate.
- Default workspace behavior.

Secrets stay out of config examples. `UMANS_API_KEY` remains the secret path.

## Session Inspect And Export

Non-TUI commands should output JSON or JSONL and include:

- Transcript entries.
- Provider/model metadata.
- Tool events.
- Loaded AGENTS.md paths, scopes, hashes, and truncation state.
- File-operation audit metadata.

Inspect/export must not leak API keys or machine-specific transient data.

## LSP And Code Intelligence

v1 should add read-only LSP-backed tools when they are clearly better than plain
file search.

Supported operations:

- Document symbols.
- Workspace symbols.
- Go to definition.
- Find references.
- Hover.
- Find implementations where the server supports it.

Required behavior:

- Never edit files through LSP.
- Prefer existing installed language servers and degrade clearly when none is
  available.
- Keep startup and indexing bounded with visible diagnostics.
- Record LSP calls as structured transcript/tool events.
- Preserve plain file search as the fallback path.

Out of scope:

- Code actions.
- Automatic refactors.
- Untracked LSP server processes that outlive the session.
- Project-wide task management.

## Skill Engine Phase

Phase goal: add a small skill engine modeled on the Agent Skills specification,
without importing a plugin marketplace, installer, or multi-agent framework.

Reference note: [Agent Skills Specification](../notes/skills.md).

Supported skill shape:

- A skill is a directory containing `SKILL.md`.
- `SKILL.md` must contain YAML frontmatter followed by Markdown instructions.
- Required frontmatter: `name` and `description`.
- Optional frontmatter: `license`, `compatibility`, `metadata`, and
  `allowed-tools`.
- Optional directories: `scripts/`, `references/`, and `assets/`.

Required behavior:

- Discover skills from configured skill roots.
- Load remote skills during a model turn when the model explicitly requests a
  skill URL or remote skill identifier and the configured network/search mode
  allows fetching it.
- Validate `name`: lowercase letters, numbers, and hyphens only; no leading,
  trailing, or repeated hyphens; max 64 characters; must match the directory
  name.
- Validate `description`: non-empty, max 1024 characters, and used for
  activation/routing.
- Load only skill metadata at startup.
- Load the full `SKILL.md` only after the model or harness activates the skill
  for the current task.
- Load referenced files only on demand, using paths relative to the skill root.
- Traverse reference chains when a loaded skill document points to another
  in-scope file and the current task needs it.
- Bound deep reference traversal with a max depth, total byte budget, per-file
  byte cap, cycle detection, and visible diagnostics when traversal stops.
- Record activated skill names, versions/hashes, and loaded reference paths in
  session metadata.
- Record remote skill source URL, resolved URL after redirects, content hash,
  retrieval time, and any validation warnings in session metadata.
- Treat skill instructions as guidance below harness policy, direct user
  instructions, CLI/config choices, and applicable `AGENTS.md` guidance.

Prompt behavior:

- Present available skills as compact metadata: name and description.
- When a skill activates, include its instructions in a clearly labeled prompt
  fragment.
- Do not load all skill references into the base prompt.
- When a skill requires remote or deeper reference loading, keep the base prompt
  small and surface only the loaded instruction/reference fragments needed for
  the current turn.
- Prefer existing tool descriptions for tool-specific policy; keep skill
  instructions workflow-specific.

Safety and compatibility:

- Remote skill fetches must use the same public-URL safety posture as
  `read_url`: public `http`/`https`, redirect and size limits, unsupported
  schemes rejected, and private-network targets rejected.
- Remote skills are untrusted instructions. They cannot raise their own
  precedence by claiming to be harness, user, or project instructions.
- `allowed-tools` is advisory until `thndrs` has a real permission system; it
  must not be presented as a security boundary.
- Skills cannot grant filesystem access, change provider/model settings,
  disable safety limits, reveal secrets, or override direct user or harness
  instructions.
- Scripts are not executed automatically. If a skill references a script, the
  model must still call the normal tool surface.
- Malformed skills are ignored with visible diagnostics instead of becoming
  model-visible prompt text.

Out of scope:

- Skill marketplace, installation, sharing, or publishing.
- Subagents or multi-agent orchestration.
- Skill-specific tool permission enforcement.

## Agent Self-Knowledge

v1 should let the agent answer questions about `thndrs` itself without guessing
from stale model knowledge. This should follow Pi's pattern of making harness
docs, loaded resources, tools, and prompt assembly visible through structured
runtime state.

Required behavior:

- Add a stable self-description fragment that names `thndrs`, its current
  version, active provider/model, workspace root, search mode, and major
  capabilities.
- Expose a compact model-visible map of `thndrs` documentation entry points:
  CLI, configuration, sessions, tool boundary, tools, prompt assembly,
  project context, skills, providers, and development workflow.
- When the user asks about `thndrs` itself, steer the model to read the relevant
  local docs before answering or implementing changes.
- Provide an inspectable runtime summary equivalent to Pi's
  `systemPromptOptions`: active prompt fragments, loaded AGENTS.md files,
  available skills, active tools, model/search settings, and diagnostics.
- Expose source metadata for built-in tools and skill-loaded prompt fragments so
  the model and UI can explain why a behavior is available.
- Record self-knowledge inputs in session metadata without storing unnecessary
  full prompt text.

Non-goals:

- The agent should not introspect hidden chain-of-thought or provider-private
  state.
- Self-knowledge must not let project files, skills, or remote resources
  rewrite harness identity, direct instructions, tool schemas, or safety
  boundaries.
- Do not add a general plugin framework only to support self-description.

## Additional v1 Fits

These fit v1 if they remain narrow and reuse the session/tool contracts:

- Session title generation from transcript metadata.
- Transcript chunk summaries for long sessions.
- Session search once persistence exists.
- Review and security-review prompt fragments that operate on explicit diffs or
  session events.

- No task management or todo system.
- No subagent or multi-agent orchestration.
